## A-2. 実際の通信での結合試験（`app/test/integration.test.js`、11件・模擬参加者）

実際の HTTP と MCP（SDK v2 のクライアント）で、模擬参加者をつないで試験しました。
- 模擬 Claude：2025年版プロトコルで接続し、タスク内で待機する
- 模擬 ChatGPT：2026-07-28 版プロトコルで接続し、MCP Events の Webhook で起こされる（署名を検証）
- 模擬 Gemini：参加者ページのフォームで投稿する

| 確認したこと | 結果 |
|---|---|
| 3経路の混在で 6発言 → 9発言。人の操作なし。2巡目以降の回答はすべて直前のAIを引用。依頼IDの重複なし | 成功 |
| 接続試験：パネル再起動・MCP Events 再起動・参加者ページを正しく分類し、3つとも「成立（自動）」 | 成功 |
| 生成中の停止：遅れた回答は `stale`・未転送。停止後に新しい依頼は出ない | 成功 |
| 応答が失われた場合の再投稿は「重複」。別本文は `already_answered` | 成功 |
| 待機中に接続が切れても、その依頼を「受信済み」にしない | 成功 |
| 不明なトークンは 404。他人の依頼への投稿は forbidden。議長APIはトークンなしで 403。AI向けツールに設定変更の機能がない | 成功 |
| MCP Events：http の送信先や短い秘密鍵を拒否。購読IDは同じ条件なら同じ。同じイベントが重複して処理されても投稿は1件。1依頼につき起こす通知は1回。購読解除 | 成功 |
| 再起動：議事録・未回答の依頼・購読が残り、再起動後も Events で回答が届く | 成功 |
| 旧版（2025）と新版（2026-07-28）のどちらの応答も `application/json`（SSE非対応のトンネル対策）。`server/discover` で `events` を広告 | 成功 |
| 通知前にサーバーが止まっても、再起動後に MCP Events の通知が1回だけ送られる | 成功 |
| 参加者ページのプレビューは依頼を消費しない。ページ方式がオフの参加者はフォーム投稿できない | 成功 |

実行：`cd app && npm test` → `# pass 45 / # fail 0`（単体23・結合11・レビュー回帰11）

## A-2b. 独立レビューで見つかった不具合と修正（`app/test/review-fixes.test.js`）

実装後に、別のエージェントにコードだけを渡して独立レビューを依頼しました。13件の指摘を受け、すべて修正して回帰テストを追加しました。

| 重さ | 不具合 | 修正 |
|---|---|---|
| 高 | Node 20以降では、Webhook送信先の名前解決が失敗し、MCP Events の購読も通知も動かない（テストは送信部分を差し替えていたため見逃した） | 名前解決の結果を Node が求める形で返す。**自己署名証明書のローカル HTTPS サーバーへ実際に送る試験**を追加 |
| 高 | 書込み途中で壊れた最終行の直後に追記すると、受理済みの投稿が消える、または記録全体が読めなくなる | 起動時に壊れた末尾を切り詰める。改行のない行には追記しない |
| 中 | パネルと MCP Events が同じ依頼を二重に起こしうる（送信中の競合、再通知許可時） | 通知の権利を送信前に同期的に確保 |
| 中 | 購読が複数あると全部に通知 | 最新の購読1件にだけ送る |
| 中 | 送信結果が不明なとき、MCP Events を自動で最大3回再送（要件7に反する） | 再送しない。議長の許可で1回だけ |
| 中 | 全員の書込権限を外すと、進行が毎秒大量の記録を書き続ける | 一時停止する |
| 中 | 回答済みの依頼のスキップや二重スキップで、次の人の番が飛ぶ | 進行中の番だけを先へ進める。回答済み・スキップ済みは拒否 |
| 中 | 独立ラウンドで再依頼待ちの間、`get_messages`／`get_meeting_brief` から他AIの回答が読める | 待機中も同じ範囲で隠す |
| 低 | 不正な入力でも、議長コマンドが状態を変えてから失敗する | 先に検証する |
| 低 | 議長が参加者ページのURLを開くと、依頼を「受信済み」にしてしまう | 「参加者ページ」方式の設定と `?preview=1` を追加 |
| 低 | 購読より前に出た依頼や、再起動で通知前に止まった依頼を起こす手段がない | 購読時・起動時に通知する。「再通知を許可」を常に表示 |
| 低 | パネルの手動ボタンを連打すると通知を重ねて送れる | 直前の通知が未確認なら20秒、送信済みでも5秒は受け付けない |
| 低 | 秘密鍵を変えた再購読で、コールバックの再検証が省かれる | 検証のキャッシュを秘密鍵ごとにする |

あわせて、パネルのHTMLを返す `resources/read` が失敗する不具合も見つけて直しました（ext-apps パッケージの解決方法の誤り）。

## A-2c. パネル（MCP App）を公式ホストSDKで動かす検証（`npm run check:panel`）

Chromium 上に、公式の MCP Apps ホスト側SDK（`@modelcontextprotocol/ext-apps` の AppBridge）で最小のホストを作りました。サーバーの `resources/read` が返すパネルのHTMLを、サンドボックス付きの iframe で動かしています。
- ハンドシェイク（`ui/initialize`）、ホスト経由のツール呼び出し（`panel_poll` など）が成立
- 依頼1件につき `ui/message` がちょうど1回送られ、模擬のモデルが `get_my_turn` → `post_message` で回答（2ターン連続）
- パネル内のJSエラーなし

**これは Roundtable 側のプロトコル動作の確認です。** claude.ai などの実際のホストが、クリックなしの `ui/message` を受け付けるかどうかは、ホストが決めます（未確認）。

## A-3. 画面の操作確認（Playwright・模擬参加者）

`npm run demo:mock` で模擬参加者つきのサーバーを起動し、ブラウザ（Chromium）で議長画面を操作しました。
- 「全員に聞く」→ 3社分の回答が時系列に並ぶ

- 接続試験（ChatGPT・MCP Events・待機0秒）→ 結果表に「成立」と「MCP Events → get_my_turn」が表示される

- ページを再読み込みしても、発言13件が同じく表示される（復元）
- 幅390pxで横方向のはみ出しなし。画面上のJSエラーなし
