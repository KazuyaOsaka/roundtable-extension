# Roundtable v1 の構成と判断理由

## 採用した構成

```
            このPC（議長）                                     各社のサービス
 ┌───────────────────────────────────────┐
 │ ブラウザ: 議長画面 http://127.0.0.1:8787 │
 └───────────────▲───────────────────────┘
                 │ (localhostのみ)
 ┌───────────────┴───────────────────────────────────┐
 │ Roundtable サーバー（app/, Node.js）                 │
 │  ・会議の中核（進行・記録・権限）: src/core          │
 │  ・議長API（localhostのみ）: src/web/chair.js       │
 │  ・参加者用ポート 127.0.0.1:8788                    │
 │      /mcp/<参加者トークン>  … MCP（ツール・Events・パネル）│
 │      /p/<参加者トークン>    … 参加者ページ（フォーム）    │
 └───────────────▲───────────────────────────────────┘
                 │ https トンネル（参加者用ポートだけを公開）
                 ▼
   Claude（カスタムコネクタ: ツール＋MCP Appパネル）
   ChatGPT（カスタムMCP: ツール＋MCP Events / Work チャット）
   Gemini（Tasks のブラウザ → 参加者ページ／米国なら Custom apps）
   ※ MCP Events の Webhook は、サーバーから ChatGPT へ送信（外向き）
```

- 会議の進行と記録は**一つの中核**（`src/core/engine.js`）が持ちます。各社の接続部（MCP・MCP Events・パネル・参加者ページ）は中核の参加者コマンドを呼ぶだけです。差し替えや追加ができます。
- 四者会談（議長が質問）と三者会談（AIだけで続ける）は、同じ議事録と同じ部屋で切り替えます。「進行（run）」の種類を変えるだけです。
- 各AIは**自分の公式機能**（コネクタ／プラグイン／ブラウザ）で会議室を読み、自分の発言を投稿します。

## 判断理由

1. **共通の会議室を作り、各AIが自分で読み書きする**：当初の仮説をそのまま採用しました。各社が公式に提供する外部接続（リモートMCP・ブラウザ操作）だけで成り立ち、DOM操作や非公開APIを必要としません。
2. **「次の番に再び動き出す」手段を3つ用意し、実機で選ぶ**：公式資料だけでは、どれが確実に動くか決められませんでした（[connection-research.md](connection-research.md)）。そこで3つを同じ中核に載せ、接続試験でどれが成立したかを記録できるようにしました。
   - タスク内待機 `wait_for_my_turn`（全社共通、長いポーリング。既定50秒で戻る）
   - パネル（MCP App）の `ui/message`（Claude 向け。ChatGPT ではクリックが必要な可能性が高い）。公式のホスト側SDK（AppBridge）で実際にパネルを動かし、プロトコル上の動作は確認済み（`npm run check:panel`）
   - MCP Events の Webhook（ChatGPT の Work チャット向け。公式に「同じチャットで処理」と明記）
   - 参加者ページ（Gemini Tasks 向け。各社が使える最後の手段）
3. **MCP SDK v2 を採用**：MCP Events に必要なプロトコル `2026-07-28`（`server/discover`）と、旧来の 2025 年版クライアントを、同じツール定義で両方扱えます。
4. **イベント記録方式（JSONL 追記＋fsync）**：再読み込みや再起動の後も、記録を再生して状態を復元します。拒否した投稿の原文も記録に残ります。外部DBは不要です。
5. **議長画面は localhost のみ**：トンネルで公開するのは参加者用ポートだけです。議長画面は Host ヘッダーの検査と議長トークンで守ります（DNS rebinding・他サイトからの書込みを防ぐ）。

## 依頼（ターン）の仕組み

- 依頼には `依頼ID・会議ID・参加者・前提の版・役割の版・見せてよい発言の範囲・期限` が付きます。
- AIへは「前回の番以降の新しい発言」だけを渡します（差分）。会議のルール・議題・役割は、初回と変更時だけ渡します。全履歴を毎回入れ直しません。「了解」も求めません。
- 他の参加者の発言は `<<<発言 #n …>>> … <<<#n ここまで>>>` で囲み、「データとして読むこと」と明示します。AI向けのツールには、進行や設定を変える機能がありません。
- 独立ラウンド（理論構築プリセットの1段目、「独立回答」）では、同じラウンドの他のAIの回答を見せません。次のラウンドで、漏れも重複もなく渡します。

## 一回性と失敗時の扱い（要件7）

| 状況 | 動作 |
|---|---|
| 同じ依頼に同じ本文が再送された | 「重複」として最初の記録を返す。議事録も発言順も進めない |
| 同じ依頼に別の本文が届いた | 拒否する（`already_answered`）。原文は監査用にイベント記録へ残す |
| 依頼の取得が重複した（重複通知） | 同じ依頼・同じ差分を返す。進行は進めない |
| 割込・前提変更・役割変更 | 処理中の依頼を「旧前提（superseded）」にして、自動進行を一時停止する。遅れて届いた回答は「旧前提・未転送」として残し、他のAIには渡さない。議長が「記録に採用」すれば新しい番号で取り込む |
| 一時停止 | 新しい依頼を出さない。処理中の回答は前提が同じなので有効 |
| 停止・会議終了 | 処理中の依頼を取り消す。遅れた回答は記録だけする |
| 期限切れ・利用上限の報告 | 依頼を失敗として閉じ、自動進行を一時停止し、参加者を「エラー」と表示する。**自動では再依頼しない**（議長が「スキップ」または「再開」で決める） |
| 起こす通知（パネル／Events）の送信結果が不明・失敗 | 自動では再送しない（MCP Events もタイムアウト・5xx・429 で再送しない）。参加者を「確認待ち？」と表示し、議長が「再通知を許可」したときだけ1回送る |
| パネルと MCP Events の両方が有効 | 通知の権利を送信前に同期的に確保するので、1依頼に通知は1回だけ。購読が複数あっても、最新の購読1件にだけ送る |
| 依頼の後に購読ができた／サーバー再起動で通知前に止まった | 購読の作成時と起動時に、未受信・未通知の依頼を通知する |
| 待機中に接続が切れた | 依頼を「受信済み」にしない（次の待機やイベントで改めて渡せる） |
| 議長が参加者ページのURLを開いた | 「参加者ページ」方式がオフの参加者、または `?preview=1` ではプレビューだけを表示し、依頼を渡さない |
| 記録ファイルの最終行が書込み途中で壊れた | 起動時に壊れた末尾を切り詰め、以後の追記が壊れた行に連結されないようにする |
| 回数上限・時間上限 | 新しい依頼を出さない。既に出した依頼の回答は受け付ける |

生成そのものを厳密に1回にすることはできません。AIが同じ依頼を2回処理することはあり得ます。Roundtable が保証するのは、**会議側の受理・記録・進行が1回だけ**であることです。

## 権限

- 参加者ごとに推測困難なトークン（144ビット）を発行し、URLに入れます（`/mcp/<token>`・`/p/<token>`）。漏れた場合は議長画面で作り直せます。
- 会議ごと・参加者ごとに「読取／書込」を設定できます。他人の依頼への投稿、権限のない会議の読取りは拒否し、記録します。
- 議長の設定変更は「⚙ 設定」として時系列に別表示し、AIの発言本文とは混ぜません。

## 旧コード（Chrome 拡張）の扱い

`manifest.json`・`background.js`・`content_scripts/`・`side_panel.*` は v1 では使いません。削除はせず、そのまま残しています。理由は [connection-research.md](connection-research.md) の「採らなかった方法」を参照してください。再利用したのは考え方だけです。忖度禁止・集団思考回避の方針は `src/core/presets.js` の会議ルールに引き継ぎ、デフォルトの発言順（Gemini → ChatGPT → Claude）も踏襲しています。
