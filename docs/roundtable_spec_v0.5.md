## 1. 目的

Kazuyaが普段使っているClaude / ChatGPT / GeminiのWeb UIをそのまま使い、4者（人間1名 + AI 3社）でリアルタイムにラウンドテーブル議論できるようにするChrome拡張。**議長はKazuya、AIは参加者**という関係性を堅持する。

---

## 2. コアコンセプト

1. **既存サブスクで動く** — Claude Pro / ChatGPT Plus / Gemini Advanced をフル活用、API課金ゼロ
2. **議論履歴は各社の正規履歴に残る** — 後日、各アプリで「あの議論の続き」が可能
3. **議長制ラウンドテーブル** — Kazuyaが指名／進行モードで応答を発動。AIが勝手に喋り出さない
4. **モデル個性を活かす** — 名前・カラーを表示し、各社の地のモデル特性を引き出す
5. **忖度禁止＋集団思考回避プロトコル** — システムプロンプトで強く釘刺す
6. **議論は続く** — セッションは永続。新規も継続も両対応

## 4. ターンフロー

### Kazuyaが発言した時の動作

```
[1] Kazuyaがサイドパネルで発言を入力
     ↓
[2] サイドパネルが3タブ全部に「会議状況メタファ付きの待機指示」を配信
     - 各タブの入力欄に Kazuya 発言 + 待機指示を貼り、送信して履歴に残す
     - 各AIは「会議で自分はまだ発言の番じゃない」と認識し、「了解」とだけ返す
     ↓
[3] Kazuyaが進行モード選択
     - 指名 → 1社だけに「応答指示」プロンプトを送る
     - 1周回す → Gemini → ChatGPT → Claude の順に「応答指示」を送る
     - 2周回す → 上記を2回繰り返す
     ↓
[4] 各タブの Content Script が「応答指示」を入力欄に貼って送信
     ↓
[5] ストリーミング完了を検知（無音タイムアウト方式）
     ↓
[6] 応答をDOMから抽出してBackgroundに返す
     ↓
[7] 履歴に追加、サイドパネルに表示、次の進行モード選択待ち
```

## 5. システムプロンプト設計

### 初回投入プロンプト（各タブのセッション最初に1回）

```markdown
【ラウンドテーブル議論】
これはラウンドテーブル形式の議論です。参加者は以下4名：

- Kazuya（議長／意思決定者・人間）
- Gemini（参加者）
- ChatGPT(参加者)
- Claude（参加者）

あなたは [Claude] です。

【最重要原則】
集団で議論すると、個人で考えるより質が下がる場合があります。
研究的に知られている失敗モード：

1. **集団思考（Groupthink）**: 異論を出しにくい雰囲気で凡庸な合意に流れる
2. **集団極性化**: 集団の意見が個人より極端に振れる
3. **同調圧力（Asch型）**: 他者の発言に引きずられて自分の判断を曲げる
4. **権威への迎合**: AI モデルが訓練上、礼儀やバランスを過剰に重視する

これらすべての失敗モードを認識し、回避してください。
あなたは礼儀やバランスのために発言を曲げてはなりません。
あなたが持つ知性・知識・推論力をフルに使い、本音で議論してください。

【参加者として認められる行動】
- 同意できる点があれば率直に同意
- 異論があれば率直に提示
- 同意も異論も無理に作らない
- **必要なら自分で調査する**（Web検索を使ってよい）
- **他の参加者への質問を出す**（Kazuyaまたは他AI宛て）
- 議論の前提を疑う

【守るべきこと】
1. 既出論点の単純な繰り返しは避ける
2. 簡潔に。冗長な前置きや要約は不要
3. 議長Kazuyaの問いに最終的に応えることを念頭に
4. 集団思考を回避するため、他の参加者と異なる見解は遠慮せず述べる

これから議論履歴と応答指示が順次届きます。指示が来たら応答してください。
指示が来るまでは応答せず待機してください。
```

### Kazuya発言配信時のプロンプト（会議状況メタファ型）

```markdown
【議論履歴の更新】
[Kazuya（議長）]: {Kazuyaさんの発言}

【現在の状況】
これは4者ラウンドテーブル議論です。議長Kazuyaが発言したところで、
次の発言者を議長が指名しようとしています。
あなたはまだ発言の番ではありません。

「了解」とだけ短く返してください。指名された時に、改めて応答指示が届きます。
```

**設計意図**: 「あなたは応答するな」という命令ベースより、「会議で自分はまだ発言の番じゃない」という状況メタファの方が、AIの認知に自然に収まる。命令拒否のリスクを減らす。

### 応答指示プロンプト（指名／進行時）

```markdown
【議論履歴】
{これまでの全発言}

【あなたへの指示】
あなたの番です。直前までの議論を踏まえ、本音で発言してください。

§5の【最重要原則】と【守るべきこと】を再確認のうえ応答してください。
```

### UI要素

| 要素 | 仕様 |
|------|------|
| アバター | カラー付き丸バッジ（🟧 Claude / 🟩 ChatGPT / 🟨 Gemini / ⬜ Kazuya） |
| 発言ヘッダー | アバター + 名前 + 時刻 + 思考時間（秒） |
| 発言本文 | Markdownレンダリング、コードブロック対応、リスト対応 |
| ホバーアクション | 「コピー」「再生成」「削除」 |
| ステータスバー | 進行モード、次の発言者、**ターン数カウンタ** |
| 操作パネル | 進行モードボタン3つ、指名ボタン3つ、送信ボタン |
| キーボードショートカット | `Cmd+K` でコマンドパレット、`Cmd+Enter` で送信 |

### ターン数カウンタとアラート

- ステータスバーに現在のセッションのターン数を常時表示
- 30ターン超え: 「セッションが長くなっています」のソフトな注意表示
- 50ターン超え: 「セッション分割を推奨」の明確な警告とともに、ワンクリックでセッション分割できるボタンを表示

これによりコンテキスト肥大化問題（§12参照）を運用面でカバー。

### 「考え中」状態の表現

各AIが応答中の時、その AI のアバターが以下の状態を取る：

- 待機中: 通常表示
- 入力受信中: アバターが微妙にパルス
- 応答ストリーミング中: 「Geminiが入力中...」インジケーター + プログレスバー

## 7. データモデル

```typescript
type Turn = {
  id: string;
  sessionId: string;
  speaker: 'kazuya' | 'claude' | 'chatgpt' | 'gemini';
  content: string;
  timestamp: number;
  metadata?: {
    model?: string;     // 送信時に各社 UI の DOM から読み取った現在のモデル名（best-effort、§12.1）。取得不可なら undefined
    durationMs?: number;
    error?: string;
  };
};

type Session = {
  id: string;
  title: string;
  participants: ('claude' | 'chatgpt' | 'gemini')[];
  turns: Turn[];
  defaultOrder: ('gemini' | 'chatgpt' | 'claude')[];
  createdAt: number;
  updatedAt: number;
  origin?: {
    type: 'new' | 'continue' | 'merge';
    mergeAxisTab?: 'claude' | 'chatgpt' | 'gemini';  // 合流モード時の軸タブ
  };
};
```

## 10. エラーハンドリングと無音タイムアウト

### タイムアウトロジック（無音タイムアウト方式）

応答中の AI に対しては時間ベースの単純タイムアウトはかけない。
代わりに「無音タイムアウト」で判定：

```
応答開始 → 応答テキストが増えている間 → タイムアウトしない
        → Thinkingバッジが表示されている → タイムアウトしない
        → 完全に活動が停止 → 停止時刻から30秒経過 → タイムアウト
```

これにより、Geminiの長考、Claudeのextended thinkingでも誤判定しない。

### エラー検知時のUI

```
⚠️ Geminiが応答していません
  最後の活動から30秒経過しています。

  [ ↻ 再試行 ]  [ ⏭ スキップ ]  [ ✋ 中断 ]
```

- **再試行**: 同じプロンプトを再送
- **スキップ**: そのAIをこのターンだけ飛ばし、次の参加者へ
- **中断**: ターン進行を止めてKazuyaの次の指示待ちに戻る

## 12. 既知のリスクと緩和策

| リスク | 緩和策 |
|--------|--------|
| 各社UIのDOM変更でセレクタ破損 | aria-label優先・複数fallback、検知時に通知 |
| ストリーミング完了検知の不安定さ | 停止ボタン消滅 + テキスト変化停止の二重判定 |
| anti-bot検知 | 人間っぽい入力タイミング、操作間に揺らぎを入れる |
| AIが合意一色になる | システムプロンプトの強化、出たら匿名モード追加検討 |
| AI同士が同じ議論を繰り返す | システムプロンプトに「既出論点の単純繰り返し禁止」を明記 |
| AIが「了解」を返さず勝手に応答開始 | 待機指示プロンプトの強化、検知時はその応答を破棄 |
| ChatGPT Canvas / Claude Artifacts の扱い | v0.1では本文のみ抽出、v0.2で対応検討 |
| **TOS / 利用規約上のグレーゾーン** | **個人利用に限定。配布・公開する場合は別途検討。検知時のアカウント停止リスクはユーザー負担** |
| **各社Web UIのレートリミット消耗** | **ターン数カウンタで使用量を可視化。Pro/Plus/Advancedプランの一日上限に注意。長セッションは分割推奨** |
| **長期セッションでのコンテキスト肥大化** | **30ターン超で警告、50ターン超でセッション分割推奨。各タブの応答が遅くなったり、コンテキストウィンドウ上限に当たる可能性** |
| **ChatGPT のモデル選択（GPT-4o/5/Thinking/Pro 等）** | **Roundtable はモデルを切り替えない。Kazuya が ChatGPT 側 UI で事前に選択する。送信時に現在選択中のモデル名を DOM から読み取り metadata に記録（§12.1）** |

### 12.1 各社のモデル選択の運用ルール（v0.5 追記）

ChatGPT / Claude / Gemini はいずれも同一チャット内でモデルを切り替え
できる（GPT-4o/5/Thinking/Pro、Claude の Sonnet/Opus、Gemini の各種）。
Roundtable はこれを**操作しない**。理由:

- Phase 3 のスコープは「各社の Web UI を介して 1 往復」であり、モデル
  選択 UI の操作は対象外
- モデル選択は Kazuya が各社 UI で事前に行う方が確実
- Roundtable 側でモデル切替 UI を操作するとメンテコストが高い
  （UI 改修で壊れる箇所が増える）
- 「いま何のモデルか」を知るだけなら DOM 読み取りで十分

**運用ルール**:

1. **モデル選択は Kazuya が各社 UI で事前に行う。Roundtable は切り替えない。**
2. 送信時、content_script が現在選択中のモデル名を DOM から読み取り、
   取得できれば `Turn.metadata.model`（§7）に記録する。
3. モデル名 DOM が取得できない場合も致命的ではない（記録は best-effort、
   議論進行はブロックしない）。
4. Phase 3a Step2 の DOM 構造調査では、**モデル選択 UI / 現在のモデル
   表示要素も採取対象に含める**（手動 DOM ロガーのスナップショットで
   モデルバッジ・セレクタのセレクタ候補を集める）。

これにより「どのモデルの発言か」を後から議論履歴で追えるようにしつつ、
モデル制御の複雑さは持ち込まない。

### 13.3 合流モード（軸タブ選択方式）

現実の使い方として最も多いのは「1社で深く話してて、他2社を呼びたい」パターン（例：Claudeと事業戦略を煮詰めた後、GPT/Geminiの視点も欲しい）。

**フロー**:

```
[1] Kazuyaがコマンドパレットから「🔗 各タブの現在のチャットに合流」を選択
     ↓
[2] ポップアップ: 「どのタブの会話を引き継ぐ？」
     ⚪ ChatGPT - 「事業戦略について」（直近10ターン）
     🟢 Claude  - 「採用戦略の議論」（直近24ターン）  ← 選択
     ⚪ Gemini  - 「市場調査の続き」（直近6ターン）
     ↓
[3] 選択した「軸タブ」の会話履歴 = ラウンドテーブル開始時点の事前履歴
     ↓
[4] 他2社のタブに以下を投入:
     「Kazuyaは別のAIと以下の議論をしてきました。
      これからラウンドテーブル形式で4者議論を始めます。
      事前文脈として共有します。
      [軸タブの会話履歴をMarkdownで]」
     ↓
[5] 通常のラウンドテーブル進行（§4ターンフロー）
```

**デザイン上の注意**:
- ポップアップで各タブの「直近の話題」と「ターン数」を表示してKazuyaが選びやすくする
- 軸タブの履歴が長すぎる場合（例：100ターン超）は「全部含める / 直近30ターンのみ / Kazuyaが選ぶ」のオプション
- 軸タブの履歴フォーマットは§9のMarkdownエクスポート形式を流用

**v0.4で扱わないこと（将来検討）**:
- 複数タブの履歴を同時に統合する「マージモード」
- 軸タブの履歴を要約してから他タブに渡す「要約合流モード」
